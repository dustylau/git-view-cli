# Rust versus Go

Decision: Open. Research checked against primary project documentation on 2026-11-22. No prototype or performance benchmark has been run. Library names below are candidates, not installed application dependencies; pin compatible versions and verify licenses/advisories after selection.

## Is Rust a good candidate?

Yes. Rust supports the required Windows, macOS, and Linux targets, including relevant x86-64 and ARM64 targets. Ratatui with Crossterm provides a viable terminal stack. There is no identified requirement that disqualifies Rust. The earlier preference for Go emphasized development simplicity and cross-build convenience, not a deficiency in Rust. See [Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html) and [Ratatui's backend documentation](https://ratatui.rs/concepts/backends/).

This application's design delegates expensive Git semantics to the Git process. It is reasonable to expect Git queries, filesystem access, and rendering choices to matter more than language alone for many operations, but that is an architectural hypothesis, not a measurement. Do not claim either implementation will be faster or smaller without equivalent experiments.

## Pros and cons

The implementation-effort judgments below are project assessments. Team experience can reverse them; verify them during the experiment.

| Dimension             | Go strengths                                                                                                | Go costs/risks                                                                                          | Rust strengths                                                                                                       | Rust costs/risks                                                                                                         |
| --------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Initial delivery      | Small language and goroutines can simplify Git/watcher workers; Bubble Tea supplies a cohesive event model. | Concurrency lifetimes and shared state still need deliberate design and race testing.                   | Expressive enums and ownership can model session state and resource ownership explicitly.                            | Ownership/lifetimes and event-loop integration add learning and design work, particularly for a team new to Rust.        |
| Long-running sessions | Built-in runtime, channels, and context are convenient for cancellable work.                                | Garbage collection adds allocation/runtime considerations; measure rather than assuming visible pauses. | Ownership-based memory management needs no garbage collector; Send/Sync restrict unsafe thread sharing in safe Rust. | Compiler checks do not prevent deadlocks, all logical races, unbounded queues, or leaked child processes.                |
| Terminal UI           | Bubble Tea/Bubbles/Lip Gloss form a coordinated ecosystem.                                                  | Framework-specific update/command patterns and API versions require learning.                           | Ratatui provides flexible layouts and testable rendering; Crossterm covers terminal I/O.                             | More application-owned decisions about input routing, widgets, worker events, and terminal handoff.                      |
| Builds/distribution   | Pure-Go cross-compilation is straightforward when the dependency graph avoids cgo.                          | cgo/native dependencies change that story; OS/terminal tests are still mandatory.                       | Native binaries and explicit compilation targets support all required OS families.                                   | Cross-building can require target linkers/SDKs; Linux libc compatibility and Windows toolchain choice need release work. |
| Runtime cost          | Suitable design for a Git-subprocess-heavy app; simple worker architecture.                                 | No ownership-based control over allocation lifetimes; memory and runtime costs need measurement.        | Fine-grained allocation/resource control and no GC are useful if measured budgets require them.                      | Tuning can consume effort without improving Git subprocess latency; no measured advantage yet.                           |
| Testing/workflow      | Built-in testing, race detector, formatter, vet, and Godog fit the workflow.                                | A passing race run does not prove absence of races or process lifecycle defects.                        | Cargo tests, rustfmt, Clippy, cucumber-rs, and CLI testing crates fit the workflow.                                  | Feature combinations and test harness configuration need care; native terminal tests remain necessary.                   |

For language/runtime facts, see [Go concurrency guidance](https://go.dev/doc/effective_go#goroutines), [Go's GC guide](https://go.dev/doc/gc-guide), [Rust ownership](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html), and [Send/Sync](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html). For cross-build constraints, see [Go's FAQ](https://go.dev/doc/faq) and [Rust target/linker options](https://doc.rust-lang.org/rustc/codegen-options/index.html).

## Monitoring differences worth testing

fsnotify documents that directories are not watched recursively automatically and that some network/virtual filesystems do not provide suitable native events. notify documents its own filesystem/backend caveats and provides PollWatcher. In either stack, test atomic editor saves, new directories, Git index replacement, external commits, linked worktrees, event overflow, and periodic reconciliation. See [fsnotify's FAQ](https://github.com/fsnotify/fsnotify) and [notify's known problems](https://docs.rs/notify/latest/notify/).

## Reusing diff and merge tools

Git remains the diff engine in both candidates. [delta](https://github.com/dandavison/delta) is an optional external syntax-highlighting presentation tool usable by either stack; its implementation language does not make it a ready-made Rust UI widget. Use [git difftool](https://git-scm.com/docs/git-difftool) and [git mergetool](https://git-scm.com/docs/git-mergetool) for explicit user-selected tools. Suspend the TUI around external terminal ownership.

If a later requirement needs comparison of text that Git cannot supply, first evaluate an existing library such as Rust's [similar](https://docs.rs/similar/latest/similar/). That is not a reason to add another diff engine now. A Rust Git library such as git2 or gix is likewise outside the current Git-CLI-first design.

## Decision experiment

Run one bounded experiment per candidate in a future M1 increment, with the same fixtures and visible behavior:

- Discover a repo and parse NUL-delimited porcelain v2 status for clean/dirty, staged/unstaged, rename, Unicode, unborn HEAD, and linked-worktree cases.
- Render a changes list with keyboard selection, resize handling, and a Git patch viewport. Exercise plain CLI output and selected Watch views.
- Refresh after atomic saves and external Git changes; verify polling/reconciliation and stale-result handling.
- Hand off to a foreground editor, return to the same view, and restore the terminal after success, launch failure, cancellation, and application error.
- Execute one real Gherkin scenario, unit tests, formatting, and static analysis on Windows, macOS, and Linux.
- Build candidate release artifacts and record target/linker/runtime prerequisites. Use the same Git version and repo fixtures where possible.

Record implementation effort, unresolved lifecycle defects, clean/incremental build times, startup/status latency, idle CPU, memory, refresh latency, and binary size. Record exact hardware, OS, terminal, compiler, dependencies, build options, repository size, and repeated-run methodology. Include the Git-only baseline. Do not compare a Go debug build with an optimized Rust release build.

Decide in this order: all functional/portability gates pass; terminal and child-process lifecycle are reliable; maintenance effort is acceptable; distribution is reproducible; measured resource costs meet agreed budgets. Budget thresholds must be set in the M1 plan before measurement. If both satisfy the gates, team fluency and measured implementation complexity should resolve the choice. Write the evidence and accepted decision into the [ADR](adr/0001-application-stack.md).

No prototype was executed in DOC-001. Neither Go nor Rust is installed in the current local environment. The comparison provides enough evidence to treat both as credible candidates; it does not select the winner.
